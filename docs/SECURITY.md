# 安全设计

本文档说明权限、身份与审计三块的设计，以及**诚实的边界清单**——哪些威胁当前能防、哪些防不了、什么时候补。

## 1. 文档级 ACL

### 密级模型

四级密级，宁高勿低：

| 密级 | 典型内容 | 默认可见 |
|---|---|---|
| public | 企业简介、产品公开资料 | 所有身份含访客 |
| internal | 制度、流程、SOP | 员工及以上 |
| restricted | 台账、预算、合同流转 | 按组授权（管理层/财务部等） |
| confidential | 工资、薪酬 | 仅 admin |

### 自动定密

入库时 `classify_document()` 按文件名规则自动定密（工资/薪酬→confidential；合同/竞业→restricted；制度→internal……），管理员可手动覆盖。定密规则只有这一处实现——**单一事实源**。

### 双层一致（本系统最重要的安全教训）

密级同时存在于两处：registry 台账（事实源）与 Milvus 向量行（检索过滤依据）。历史上只改台账不同步向量库，导致员工仍能检索到涉密文档（真实事故，员工查到总经理工资）。修复后：

- `update_doc_access()` 以"查询→删除→重插"同步向量行，带 chunk_id 去重防御
- 存量数据用 `apply_acl.py` 全量刷新
- 6 条 ACL 用例进 L1 门禁（4 拦截 + 2 护栏），基线 1.0，回归不过不能合并

### 过滤位置

ACL 在 **Milvus 查询表达式层**过滤，无权文档块不离开数据库——区别于"检索后过滤"（浪费召回名额且内存短暂接触敏感内容）。

## 2. 身份鉴权

- **凭据**：PBKDF2-SHA256 十万轮散列 + 常数时间比较（防时序攻击）；登录失败对存在/不存在的用户走相同散列路径
- **令牌**：JWT HS256，8 小时有效期，密钥首次启动自动生成并持久化
- **身份解析**：所有业务端点从 Bearer 令牌解出身份（user_id/role/groups），请求体中的角色字段在鉴权开启时被完全忽略——伪造请求实测 401
- **登出即吊销**：jti 进黑名单文件（重启不丢、过期自动清理），被偷令牌立即失效；按 jti 隔离，单设备登出不影响同账号其他会话
- **评测兼容模式**：`AUTH_REQUIRED=0` 时退回请求体身份，仅限内网评测/压测，生产禁用

## 3. 审计日志

- **覆盖**：检索（含命中文档密级、`sensitive_hit` 标记）、答案（拒答与否、长度、引用文档、是否调用 LLM）、文档操作（上传/删除）、登录事件
- **脱敏**：查询文本先经 PII 脱敏（手机号/身份证等）再落盘；答案只记长度不记全文
- **可查性**：按天 JSONL；`/api/audit/summary`（仅 admin）出统计与最近敏感命中明细；前端运维页告警灯
- **关联**：search 与 answer 事件以 query_hash 串成完整链路

## 4. 已知边界与迁移触发条件

| # | 边界 | 风险 | 补齐条件 |
|---|---|---|---|
| 1 | 用户表/密钥为本地文件 | 单机可接受；多副本不一致 | 多副本部署时进数据库 + KMS |
| 2 | JWT 黑名单为本地文件 | 同上 | 多副本时换 Redis |
| 3 | 审计 JSONL 无防篡改保护 | 本机攻击者可改日志 | 等保三级/外部审计要求时上哈希链或独立存储 |
| 4 | 演示账号密码公开于 README | 仅影响未改密码的部署 | 部署清单强制首步改密 |
| 5 | 无登录频率限制 | 弱密码可被暴力尝试 | 公网暴露前加速度限制 |
| 6 | 身份为本地账号体系 | 无 SSO | 企业微信/钉钉 OAuth 适配器接口已预留（AuthProvider） |

## 5. 上线前强制清单

1. 修改全部演示账号密码（或禁用，仅保留真实账号）
2. 更换 JWT 签名密钥（删除 `auth_secret.key` 重启即自动生成新密钥，注意会话失效）
3. `CORS_ORIGINS` 收紧为具体域名
4. 关闭 `AUTH_REQUIRED=0`（若曾开启）
5. 按 §4 核对部署形态对应的边界项
