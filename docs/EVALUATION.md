# 评测方法论

本项目的核心信念：**没有回归门禁的检索优化是不可信的**。所有检索/生成分支的改动，必须先过 L1 门禁再合并。

## 1. 分层回归体系

| 层级 | 内容 | 速度 | 触发时机 |
|---|---|---|---|
| L0 | 冒烟（版本治理 + 检索 6 条 + 生成 1 条 + 拒答 1 条） | 秒级 | 每次启动 |
| **L1** | **全量门禁（本文重点）** | ~2 分钟 | 每次检索/生成分支改动 |
| L2 | 答案质量抽样（LLM 裁判：grounded/partial/ungrounded + 拒答判定，20 条） | 分钟级 | 生成侧改动 |
| L3 | L1 + 答案级全量（26 条） | ~5 分钟 | 发版前 |

## 2. L1 门禁构成（104 条用例）

| 用例集 | 数量 | 测什么 |
|---|---|---|
| seed_v2 | 26 | 标准问答召回（recall@5、MRR），全部应可答 |
| persona 可答 | 61 | 五类身份的真实问法 + 多轮指代消解（`seed_persona.json` 共 78 条，另含 11 拒答 + 6 ACL） |
| 拒答 | 11 | 库中无答案时必须拒答（含"高置信错误"陷阱题） |
| ACL | 6 | 四身份权限：4 条拦截 + 2 条护栏（防过度封锁） |

四项指标各自与 `eval_reports/regress_baseline.json` **逐位对比**（不止比较阈值），任何一项退化即失败：

```
seed_v2   recall  1.0000  = 基线   persona recall 0.9344  = 基线
seed_v2   mrr     0.9038  = 基线   persona mrr    0.7874  = 基线
拒答率 1.0 = 基线    ACL 通过率 1.0 = 基线
```

> seed 集只有 26 题、语料 56 份（584 块），recall@5 已饱和到 1.0，**单看 recall 无法区分改动好坏**；排序质量看 MRR，覆盖面靠 persona 集（61 可答）补。评测集规模本身就是这套门禁的已知上限。

运行：`python run_regress.py --level 1`

## 3. 基线生命周期

基线不是永远的标尺。**语料、标签、参数发生合法变更后，基线必须刷新**（`--update-baseline`），否则合法改进会被误报为退化。本项目经历过一次真实教训：扩容语料后旧基线引发"性能退化"假警报，排查确认是基线过期。刷新基线的操作必须与变更关联记录（见 DEVLOG）。

## 4. 用例设计原则

- **评测集测已知，用户测未知**：ACL 泄露事故（员工查到工资）评测集从未抓到，是人肉实测发现的。事故之后第一件事是把事故固化为用例——**每个修过的 bug 都应变成回归用例**
- **护栏用例与拦截用例配对**：ACL 不仅测"员工不能看工资"（拦截），也测"员工能看考勤制度"（护栏）——防止把权限修成一刀切封锁
- **陷阱题**：拒答集包含语义通顺但库中无据的问题（高置信错误），防止模型被表面流畅性带偏

### 期望解析门禁：防止用例"静默失效"

评测集不绑定 `doc_id`，而是写 `expected_base_titles`（制度名），运行时按台账解析为现行版 `doc_id`。这个设计让换数据不用改评测集，但引入一个隐蔽风险：**标题解析不到时该期望项被跳过，若全部跳过则期望为空，`recall_at_k` 兜底返回 1.0——用例从此"永久通过"**。

这不是假设。2026-10-27 语料主体名替换后，registry 的 `base_title` 未同步，7 条用例（seed_v2 4 条 + persona 3 条）的期望全部或部分解析失败。回归输出的是"轻微退化"（recall −0.019 / mrr −0.125），真相是 **5 条用例已变成空壳、2 条被削掉一半检验强度**。指标只是表象，评测能力被削才是实质。

现在每份评测报告都带三个字段，`run_regress.py` 见到非零直接判失败（与基线无关，任何数量都不允许）：

| 字段 | 含义 | 正常值 |
|---|---|---|
| `missing_expectation_count` | 至少一个期望标题解析失败的用例数 | 0 |
| `empty_expectation_count` | 期望全空 → recall 恒 1.0 的空壳用例数 | 0 |
| `missing_expectation` | 明细：用例 id / query / 缺失的标题 | 空 |

**修法不是刷基线，而是补数据**：本次用 `scripts/rename_documents.py` 把 registry 的 `filename` / `base_title` / Milvus `doc_name` 一并改名（只改元数据、不重新解析，chunk 与向量不变，指标可原地对比），指标恢复到基线。

> 通用教训：**任何"失败被兜底值掩盖"的地方都要加显式信号**。此前是向量通道静默降级（DashScope 欠费），这次是评测期望静默失效——同一类病，两种壳。

## 5. 专项实验记录（结论已沉淀）

| 实验 | 结论 | 后续动作 |
|---|---|---|
| 架构对比（向量/混合/混合+rerank） | 混合+rerank 最优 | 定为生产配置 |
| α 权重扫描（0.1~0.95） | rerank 中和效应，α 无效 | 保持 0.5，不再调 |
| 兜底通道（置信阈值补召回） | 触发 1/300，向量 miss 是高置信错误，阈值拦不住 | 路线放弃（否定性结论同样记录） |
| 并发压测（10/20/30/50） | 瓶颈在外部 API 往返；暴露 LLM 默认超时 600s 挂起 | 超时收紧 60s + 熔断 |
| 放量 1204 份合成语料 | 入库链路稳定；压测结论不可直接迁移主库 | 实验需主库验证环节 |

python mine_real_queries.py --days 7
